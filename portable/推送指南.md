# 推送指南：外壳代码放到 GitHub，Actions 自动出包

## 现状与前提

- **上游** `https://github.com/deepseek-ai/deepseek-harness`：DeepSeek 官方维护，MIT，**版本更新只认这里**（发 `dsh-v*` tag，同时把 `@deepseek-ai/dsh` 发到 npm）。你只有读权限，没有写权限。
- **本机源码副本**：工作区里的 `deepseek-harness-master\`，是官方仓的快照（`@deepseek-ai/dsh-root` 0.2.2-alpha.3，没有 `.git`）。只用来取原始图标、查实现细节，不参与构建，也不往仓库里放。
- **fork** `lentll/deepseek-harness`：从官方仓 fork，现有 `master`（上游快照）和 `protable`（外壳）两个分支。它的作用只是**提供 Actions 和存放外壳代码**，不承担源码同步。
- 本机到 GitHub 实测下载速度约 **33 KB/s**，上游仓库 353 MB —— 完整克隆要 3 小时，不可行。所以这里用**独立根分支**：`protable` 不含上游代码，只放外壳源码（约 200 KB）和 workflow，推送与 CI 都很快。

```
lentll/deepseek-harness
├─ master      上游快照（fork 创建时的官方代码，只读参考，不参与出包）
└─ protable    独立根分支：portable/ + .github/workflows/portable-build.yml
```

## 已经替你准备好的内容

本机的 `dsh-portable-repo\` 目录就是要推的东西：

| 路径 | 内容 |
|---|---|
| `portable/` | Electron 外壳源码、构建/更新脚本、签名脚本、README、推送指南 |
| `.github/workflows/portable-build.yml` | 出包 workflow |
| `推送更新.cmd` | 本机辅助脚本（已 gitignore，不进仓库） |

**已核实不含任何密钥**：仓库里搜不到你的 API Key；构建产物打包时 `data/` 会被排除，workflow 里还加了一道守卫（发现 `.env`、`.credentials.yaml` 或类似 `sk-xxxx` 的明文就构建失败）。

## 让定时任务真的会跑

GitHub 的 `schedule` **只认默认分支上的 workflow**。fork 的默认分支目前还是 `master`（GitHub API 核实过），而 `master` 上没有这个 workflow，所以**现在定时任务不会触发**。两条路，任选一条：

**A. 把 `protable` 设为默认分支（最省事）**
仓库 Settings → General → Default branch → 切到 `protable` → Update。
fork 的 master 不受影响，仍是上游快照。

**B. 默认分支保持 master，用网页把 workflow 贴上去**
在 GitHub 上 master 分支 → Add file → Create new file → 路径填 `.github/workflows/portable-build.yml` → 粘贴 `dsh-portable-repo\.github\workflows\portable-build.yml` 全文 → Commit。
（内容与 protable 上那份完全一样；任务里 checkout 的是 protable，构建用的还是外壳代码。）

不设定时也能用：Actions 页面手动 Run workflow，或改完外壳代码 push 到 protable 自动触发。

## 打开 Actions + 配签名 secret

1. Settings → Actions → General → **Allow all actions and reusable workflows** → Save
2. Settings → Secrets and variables → Actions → 新增两个：

| 名称 | 值 |
|---|---|
| `SIGNING_PFX_BASE64` | `F:\WorkBuddyData\workspace\dsh-signing\portable-signing.pfx.base64.txt` 的全部内容（3680 字符，单行） |
| `SIGNING_PFX_PASSWORD` | `F:\WorkBuddyData\workspace\dsh-signing\password.txt` 里的密码 |

不配也能跑，产物只是没有签名。**这两个值不要贴进任何仓库文件**，只能放 Secrets。

## workflow 行为

| 触发 | 行为 |
|---|---|
| 每天 20:00 UTC（北京 04:00） | 查**官方仓** `deepseek-ai/deepseek-harness` 最新 `dsh-v*` release tag → 对应 npm 版本没发过包就构建并发布 Release |
| 手动 Run workflow | 可指定版本号；勾 `force` 强制重建 |
| push 到 `protable` | 改外壳代码后自动重建，同名 Release 的附件用 `--clobber` 覆盖 |

版本映射：GitHub tag `dsh-v0.2.2-rc.1` → npm `0.2.2-rc.1`。tag 打了但 npm 还没发布时，任务会 warning 后跳过，等下一次。

产物：Release `portable-v<版本>` + `DeepSeek-Harness-portable-<版本>.7z`（约 700 MB–1 GB，**不含 data**，所以不含 API Key）。

## 上游更新怎么进来

官方仓发版后**不需要任何手动同步**：官方发 `dsh-v*` tag → 同步发 `@deepseek-ai/dsh` 到 npm → CI 下一次跑（或手动 Run）就装上这个版本，`portable/` 里的外壳代码一行都不用改。fork 的 `master` 落后多少都不影响。

只有一种情况要看源码：外壳需要跟着上游改（比如新增的 preload、改了启动参数）。这时把那版官方源码下一份快照到工作区（`deepseek-harness-master\`），对照着改外壳即可——不要在 `protable` 里 merge 上游代码，那是独立根分支，merge 需要 `--allow-unrelated-histories`，会把 353 MB 历史一并拉进来。

## 常见失败

| 现象 | 原因 / 处理 |
|---|---|
| push 报 403 | fork 不是你的账号，或登录的是另一个账号 |
| Actions 里看不到 workflow | Actions 没开启；或默认分支上没有这个文件（见上面 A/B） |
| 定时任务不跑 | 默认分支不对；或 fork 的定时任务被禁用（Actions 页面 Enable）；连续 60 天无提交 GitHub 会自动停用 |
| `npm 上还没有 x.y.z` | 上游打了 tag 但 npm 未发布，等下一次 |
| `credential files found in the build output` | 守卫生效：构建输出目录里混进了凭据文件，检查输出目录的 `data\` 是不是被误拷贝 |
| 产物被 SmartScreen 拦 | 自签名证书的预期行为；要彻底消除需付费 OV/EV 证书 |
